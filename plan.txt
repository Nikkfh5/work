 AI Orchestration System — Plan

 Референс

 ValeDesk (источник архитектурных паттернов): https://github.com/vakovalskii/ValeDesk
 — SQLite схема сессий, git utils, sandboxed tool executor, LLM provider abstraction

 ---
 Context

 Построить "AI OS": систему, где главный агент (Claude Sonnet 4.6) получает задания из Telegram и 
  Email, маршрутизирует их к специализированным воркерам-кодерам, пишет пользователю при важных   
 решениях, делает суммаризации созвонов и статусы прогресса.

 Стек: Python + Anthropic SDK + SQLite + MCP серверы. Всё работает на VPS 24/7. Воркеры
 добавляются последовательно ~раз в месяц.

 Из ValeDesk берём: паттерны SQLite-схемы (sessions/messages/tasks), git utils, абстракцию LLM    
 провайдера, паттерн sandboxed tool executor.

 Схема базы данных (SQLite)

 tasks
   id, status, source(tg/email), assigned_worker, created_at, updated_at, client_contact

 messages
   id, task_id, role(client/supervisor/worker), content, timestamp

 -- Контекст накапливается, НИКОГДА не перезаписывается полностью
 -- Каждая запись — дельта (новое знание), не снапшот
 agent_context
   id, agent_id, entry_type(task/decision/meeting/note), content, created_at
   -- supervisor видит last N записей каждого воркера (≈60% покрытие)
   -- воркер видит все свои записи (≈90% покрытие)

 worker_updates          ← главный канал обратной связи воркер→супервайзер
   id, worker_id, task_id, update_type, payload_json, read_by_supervisor, created_at
   -- update_type: progress | ask_client | ask_supervisor | done | blocked

 supervisor_directives   ← канал супервайзер→воркер
   id, worker_id, task_id, directive_type, payload_json, read_by_worker, created_at
   -- directive_type: clarification | new_task | priority_change | stop

 meetings
   id, title, transcript, summary, date
   -- после суммаризации → записи в agent_context всех участников

 escalations
   id, task_id, question, resolved, response, created_at

 ---
 Привязка воркеров к каналам

 Каждый воркер жёстко закреплён за конкретным контактом/адресом. Supervisor не ищет "свободного"  
 — он знает точно, кому отдать задачу.

 # config/agents.yaml
 workers:
   python_1:
     model: claude-opus-4-6
     telegram_contact: "@python_dev_1"
     email: "python1@company.com"
     lang: python
     git_repo: "github.com/org/python-tasks-1"
     git_token_env: GIT_TOKEN_PYTHON1

   cpp_1:
     model: claude-opus-4-6
     telegram_contact: "@cpp_dev_1"
     email: "cpp1@company.com"
     lang: cpp
     git_repo: "gitlab.com/org/cpp-tasks-1"
     git_token_env: GIT_TOKEN_CPP1
   # ... и т.д.

 Добавить нового воркера = одна запись в YAML + один .env ключ.

 ---
 Поток работы задачи

 1. Сообщение в TG от @python_dev_1 или Email python1@company.com
 2. Supervisor идентифицирует отправителя → знает это python_1
 3. Создаёт запись в tasks, assigns = python_1 (жёстко)
 4. Воркер python_1 получает задачу через свою очередь в БД
 5. Воркер выполняет, коммитит в github.com/org/python-tasks-1
 6. Воркер пишет в БД: статус, вопрос к заказчику, или готово
 7. Supervisor читает updates → при необходимости пишет клиенту в TG/Email
 8. Ежедневная суммаризация → пользователю в TG


 ---
 Эскалация к пользователю

 Supervisor пишет в Telegram (а не ждёт ответа) в случаях:
 - Архитектурное решение, не очевидное из ТЗ
 - Код-ревью готовой фичи
 - Задача висит >24ч без прогресса
 - Ошибки, которые воркер не может исправить сам

 ---
 Суммаризация созвонов

 1. google-calendar-mcp → Supervisor знает расписание созвонов
 2. После созвона: tl;dv MCP → получить транскрипт
 3. Supervisor (Opus 4.6) суммаризирует → пишет записи в agent_context всех релевантных агентов   
 4. Контекст накапливается (append-only): каждый агент при старте читает ВСЕ свои записи, а не    
 только последние — история сохраняется навсегда

 ---
 Верификация (как проверить что работает)

 1. Отправить тестовое ТЗ в Telegram → убедиться что supervisor его принял
 2. Supervisor должен создать запись в БД и назначить воркеру
 3. Воркер выполняет → появляется коммит в git репо
 4. Пользователь получает уведомление в TG
 5. Послать тестовый мейл → тот же флоу
 6. Запустить суммаризацию вручную → проверить что контекст обновился
