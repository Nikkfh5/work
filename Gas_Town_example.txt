Отличный анализ. Вот главные идеи которые реально полезны для нашего проекта:                                       
  ---                                                                                                              Что стоит взять из Gas Town             
                                                                                                                   1. GUPP принцип — уже есть в нашем плане                                                                                                                                                                                          Gas Town называет это "работа на hook → немедленное выполнение". У нас это lease_manager.py — атомарный захват   задачи из БД. Концептуально одно и то же, реализация разная (они файлы в git, мы SQLite).                                                                                                                                       
  2. Witness/Patrol — фоновый детектор зависших задач

  В Gas Town есть отдельный агент-"наблюдатель" который каждые 30 сек проверяет прогресс. У нас в плане это      
  health_monitor.py, но идея детектора зависших задач ("30 минут без обновления → эскалация") — конкретная и     
  хорошая. Стоит добавить в lease_manager.py как release_stale().

  3. Checkpoint / Handoff — у нас этого нет

  Когда у Claude Code заполняется контекст (200k токенов), Gas Town сохраняет "чекпоинт" — что сделано, что      
  осталось — и новая сессия продолжает с этого места. У нас такого нет. Это важно для долгих задач.

  4. Molecules = DAG workflows — у нас нет, но нужно?

  Gas Town умеет делать многошаговые задачи с зависимостями: шаг 2 начинается только после шага 1. У нас задачи  
  атомарные. Пока нам это не нужно, но если клиенты будут давать сложные многоэтапные ТЗ — идея полезная.        

  5. Mailbox (nudge) — у нас есть через DB

  Агенты Gas Town отправляют сообщения друг другу через файлы в .claude/mail/. У нас это через
  supervisor_directives таблицу в БД. Наш подход надёжнее.

  ---
  Что НЕ стоит брать

  ┌─────────────────────────────┬────────────────────────────────────────────────┐
  │            Идея             │                   Почему нет                   │
  ├─────────────────────────────┼────────────────────────────────────────────────┤
  │ Dolt вместо SQLite          │ Нам 2-5 воркеров, а не 30. SQLite + WAL хватит │
  ├─────────────────────────────┼────────────────────────────────────────────────┤
  │ Git как хранилище состояния │ Усложняет без выгоды, SQLite проще и надёжнее  │
  ├─────────────────────────────┼────────────────────────────────────────────────┤
  │ Отдельные ветки per-agent   │ Добавляет merge конфликты без реальной нужды   │
  ├─────────────────────────────┼────────────────────────────────────────────────┤
  │ Go стек                     │ Переписывать всё не имеет смысла               │
  └─────────────────────────────┴────────────────────────────────────────────────┘

  ---
  Единственное что реально стоит добавить в план

  Checkpoint при переполнении контекста — когда Claude Code сессия достигает лимита, сохранять в БД: что сделано,
   какие файлы изменены, что осталось. При рестарте воркер получает этот контекст в промпте.

  Это добавить в storage/schema.sql как поле partial_result в таблице tasks (уже запланировано в migrate.py) и в 
  промпт воркера при retry.

  Sources:
  - https://github.com/steveyegge/gastown
  - https://maggieappleton.com/gastown
  - https://paddo.dev/blog/gastown-two-kinds-of-multi-agent/
