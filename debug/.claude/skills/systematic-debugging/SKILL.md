# Systematic Debugging

**Когда:** тест упал, код крашится, неожиданное поведение, "не работает".
**НЕ когда:** пишешь новый код, рефакторинг, ревью, планирование.
**Граница с gh-fix-ci:** gh-fix-ci = CI в GitHub Actions. Этот скилл = любые баги локально.

## Iron Law

```
НИКАКИХ ФИКСОВ БЕЗ ИССЛЕДОВАНИЯ ROOT CAUSE
```

Если не прошёл Фазу 1 — нельзя предлагать решения.

## 4 фазы (строго последовательно)

### Фаза 1: Root Cause Investigation (ОБЯЗАТЕЛЬНА)

1. **Прочитай ошибку ЦЕЛИКОМ** — traceback, номера строк, коды ошибок. Часто ответ в самом сообщении.

2. **Воспроизведи стабильно:**
   ```bash
   pytest tests/test_xxx.py::test_name -v
   ```
   Если не воспроизводится → собирай данные, не гадай.

3. **Проверь недавние изменения:** `git diff`, `git log -5` — что менялось?

4. **Trace Data Flow** — трассируй ВВЕРХ по call stack до источника:
   ```
   Симптом → Кто вызвал? → Кто передал плохое значение? → ИСТОЧНИК
   ```
   Чини на ИСТОЧНИКЕ, не на симптоме.

5. **Инструментация** (если не видно причину):
   ```python
   logger.error("DEBUG task_id=%s value=%r caller=%s",
                task_id, value, traceback.format_stack()[-2].strip())
   ```
   Запусти → собери данные → ПОТОМ анализируй.

6. **Multi-component** — наш проект (TG → supervisor → worker → git): логируй на КАЖДОЙ границе что входит и выходит. Найди на какой границе ломается.

### Фаза 2: Pattern Analysis

1. **Найди работающий аналог** в проекте — похожий код который работает
2. **Сравни** — перечисли ВСЕ различия, даже мелкие
3. **Проверь зависимости** — что нужно чтобы работало?
4. Не предполагай "это не может быть важно"

### Фаза 3: Hypothesis and Testing

1. **Одна гипотеза:** "Причина в X, потому что Y" — запиши
2. **Минимальное изменение** — одна переменная за раз
3. **Результат:**
   - Сработало → Фаза 4
   - Не сработало → НОВАЯ гипотеза (не "ещё фикс сверху")
   - НЕ ЗНАЕШЬ → скажи "не понимаю X", не притворяйся

### Фаза 4: Fix

1. **Failing test ДО фикса** — если не видел тест fail, не знаешь тестирует ли он то что нужно
2. **Один фикс** — root cause, не симптом. Без "while I'm here"
3. **Verify:** тест проходит? Другие не сломались?
4. **Счётчик неудач:**
   - < 3 попыток: вернись к Фазе 1 с новой информацией
   - **>= 3 попыток: СТОП.** Каждый фикс ломает что-то новое = проблема архитектуры, не баг. Обсуди с пользователем ПЕРЕД следующей попыткой.

## Red Flags → СТОП, вернись к Фазе 1

Если ловишь себя на мысли:
- "Быстро пофиксю, потом разберусь"
- "Просто попробую поменять X"
- "Несколько изменений сразу, запущу тесты"
- "Наверное это X, давай починю"
- "Ещё одна попытка" (когда уже 2+)
- "Вижу проблему, давай сразу к фиксу" (пропуская Фазу 1)

## Рационализации (отвергать)

| Отмазка | Реальность |
|---------|-----------|
| "Баг простой, процесс не нужен" | Простые баги тоже имеют root cause. Процесс быстрый для них |
| "Нет времени" | Систематический дебаг БЫСТРЕЕ чем гадание |
| "Тест напишу после фикса" | Тест после фикса не доказывает ничего |
| "Несколько фиксов сразу экономят" | Нельзя изолировать что сработало |
| "Ещё одна попытка" (после 2+) | 3+ неудач = архитектурная проблема |
